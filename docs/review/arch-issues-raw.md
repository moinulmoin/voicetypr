# Architecture review — raw issues (2026-07-03 ultracode, 23 unique after workflow count)

## 1. AppContainer init effect keyed on the whole `settings` object — every settings write re-runs startup work (keyring sweep, update-service re-init, cleanup invoke)

EVIDENCE: src/components/AppContainer.tsx:56-102 — the init effect's dep array is `[settings]` (line 102). It schedules `loadApiKeysToCache()` (line 61), invokes `cleanup_old_transcriptions` (line 70), calls `updateService.initialize(settings)` (line 77), and its cleanup calls `updateService.dispose()` (line 100). `settings` is a fresh object on every write: SettingsContext optimistically replaces it (src/contexts/SettingsContext.tsx:55-58), the backend emits `settings-changed` on every save (src-tauri/src/commands/settings.rs:960), and the listener re-fetches into another new object (src/contexts/SettingsContext.tsx:102, 31-33). `loadApiKeysToCache` does `list_ai_providers` plus a keychain read per provider (src/utils/keyring.ts:92-113); `dispose()` kills the daily update timer (src/services/updateService.ts:357-362).

COST: Every toggle/keystroke-persisted setting triggers: a full OS-keychain sweep across all AI providers (slow, and on macOS can contend with keychain access), a `cleanup_old_transcriptions` DB pass, and dispose/re-create of the update-check timer — with `dispose()` racing an in-flight `initialize()` (initialize awaits `checkForUpdatesInBackground` before `setupDailyUpdateCheck`, so a dispose followed by a stale initialize can leave a timer running or none at all). Pure waste on the hot settings path plus a real timer-lifecycle race.

PROPOSED SLICE: Split the effect in AppContainer: (a) a run-once startup effect gated on the first non-null settings (ref flag) that does cleanup_old_transcriptions, loadApiKeysToCache, and the just-updated dialog; (b) an updateService effect keyed only on `settings?.check_updates_automatically` (pass a getter for current settings, or make initialize idempotent). Acceptance: a unit test (mocked `invoke`) asserting that calling `updateSettings({compact_recording_status:true})` after mount does NOT re-invoke `cleanup_old_transcriptions`/`list_ai_providers` and does not call `updateService.dispose`; existing AppContainer/Onboarding tests stay green; `pnpm typecheck && pnpm test` pass. Ships independently — no behavior change on true startup.

## 2. Model state is duplicated across two independently-fetched stores (useModelManagement.models vs useModelAvailability), and app-level routing depends on them agreeing

EVIDENCE: Both hooks fetch the same backend truth separately: src/hooks/useModelManagement.ts:138-151 (`get_model_status` into `models`) and src/hooks/useModelAvailability.ts:198-201 (`get_model_status` again, discarded except for a boolean). They subscribe to different event sets: availability listens to `model-deleted`/`stt-key-saved`/`sharing-status-changed` (useModelAvailability.ts:266-296) while useModelManagement listens only to download events (useModelManagement.ts:386-599) — a `model-deleted` from outside its own `deleteModel` leaves `models` stale while availability flips. AppContainer unmounts the entire app into onboarding when the availability copy says `hasModels === false` (src/components/AppContainer.tsx:266-270, 298), while OnboardingDesktop's readiness gate reads the *other* copy (`modelManagement.models`, OnboardingDesktop.tsx:359-373). The three-ref + setTimeout reconciliation machinery in AppContainer (lines 51-53, 211-219, 245-264) exists solely to paper over the two stores disagreeing after a `no-models-error`.

COST: Correctness: a transient disagreement (e.g. availability's `get_model_status` resolves against a pre-download snapshot while management's shows downloaded, or a model-deleted event only one store hears) flips the whole app between onboarding and main shell — the exact bug class the forceShowOnboarding ref dance was added for, and it will regrow with each new trigger event. Perf: every `model-downloaded` fires 2-3 concurrent `get_model_status` invokes (management's handler at useModelManagement.ts:522 plus availability's listener at useModelAvailability.ts:266). Maintainability: any new engine/provider must remember to update two subscription lists.

PROPOSED SLICE: Make ModelManagementProvider the single owner of the model catalog: it alone invokes `get_model_status` and subscribes to model lifecycle events (add `model-deleted` there); useModelAvailability drops its own `get_model_status` call and derives `hasModels`/`selectedModelAvailable` from the catalog passed via context plus the `get_recognition_availability_snapshot`/`recognition-availability` channel it already owns. `deriveAvailabilityState` stays pure and keeps its tests. Acceptance: grep shows exactly one `get_model_status` call site in src/; a test asserting one invoke per `model-downloaded` event; availability derivation unit tests unchanged; onboarding gate and ModelsTab render from the same object identity. Independent slice — no backend change.

## 3. Tauri event subscriptions torn down and re-registered on unstable dep identities — async re-listen gaps drop backend events

EVIDENCE: src/hooks/useModelAvailability.ts:311 — the effect registering 7 `listen()` calls depends on `[applyCanonicalAvailability, checkModels, state.selectedModelAvailable]`; `checkModels` gets a new identity whenever `settings?.current_model` changes (line 237), and `state.selectedModelAvailable` changes on most refreshes, so all 7 listeners unlisten and asynchronously re-register. Same pattern in src/components/AppContainer.tsx:243 — the 8-listener effect depends on `modelAvailability.checkModels`, so selecting a model re-registers `no-models-error`, `license-required`, etc. `listen()` is an async round-trip, so there is a window with zero subscribers. Line 290-296 shows the root cause: the `recognition-availability` handler closes over `state.selectedModelAvailable` instead of reading a ref.

COST: Correctness under exactly the busiest moment: changing `current_model` is what *causes* the backend to emit `recognition-availability`/`model-changed` (src-tauri/src/recognition/model_selection.rs:258), and that same change invalidates `checkModels` and rips the listeners down — an event landing in the re-registration gap is silently dropped, leaving `hasModels`/`selectedModelAvailable` stale (user stuck at onboarding readiness gate, or main app wrongly flipped to onboarding). Also steady-state churn: every availability refresh re-runs 7 unlisten/listen round-trips.

PROPOSED SLICE: Apply the latest-ref pattern already proven in useInAppRecordingHotkey (src/hooks/useInAppRecordingHotkey.ts:157-160): store `selectedModelAvailable` and the current `checkModels`/`current_model` in refs, make the subscription effects' handlers read from refs, and reduce deps to `[]` (availability) and `[registerEvent]` (AppContainer). Acceptance: a test that re-renders with a changed `settings.current_model` and asserts `unlisten` was NOT called; a test that an event dispatched immediately after a model change is applied to state; existing useModelAvailability/AppContainer tests green. Small, mechanical, independently shippable.

## 4. useRecording is per-consumer state, not shared — duplicate listener sets, an initial-state fetch race, and two writers to the updateService session-guard singleton

EVIDENCE: Two live instances in the main window: src/components/onboarding/OnboardingDesktop.tsx:201 and src/hooks/useInAppRecordingHotkey.ts:107 (mounted by AppContainer.tsx:48). Each instance registers its own 6 `listen()` handlers (src/hooks/useRecording.ts:52-100) and each independently invokes `get_current_recording_state` on mount (lines 34-49) with no guard: if a `recording-state-changed` event arrives while that invoke is in flight, the stale invoke result overwrites the fresher event state. Both instances also write `updateService.setSessionActive` from their own state (lines 105-108) — last writer wins on a process-wide singleton whose job is to block auto-update work during recording.

COST: Correctness: a recording started right at mount (global hotkey during app launch, or onboarding's sample recording) can regress an instance to 'idle' via the stale initial fetch; that instance then calls `setSessionActive(false)` mid-recording (defeating the update-during-recording guard) and the in-app hotkey fallback's `performToggle` reads the wrong state (useInAppRecordingHotkey.ts:201-208) and issues a duplicate `start_recording`. Perf/maintainability: 2x duplicate Tauri listeners and two divergent copies of a state machine the backend already owns; the two UIs (onboarding buttons vs hotkey fallback) can disagree about `isActive`.

PROPOSED SLICE: Two-part slice: (1) add a RecordingProvider that instantiates useRecording once (main window) and have OnboardingDesktop + useInAppRecordingHotkey consume it via context; (2) inside useRecording, guard the initial fetch with an 'events won' flag/generation token — discard the `get_current_recording_state` result if any recording event was applied first. Acceptance: test that only one `recording-state-changed` listener is registered for the main window; a race test where the event resolves before the initial invoke and state stays 'recording'; existing useRecording/useInAppRecordingHotkey/OnboardingDesktop tests green. Independent of the other slices.

## 5. Model catalog state is triplicated (useModelManagement, useModelAvailability, backend snapshot) and the onboarding gate reads a different copy than the onboarding UI renders

EVIDENCE: useModelManagement.ts:89,138-151 holds a `models` map from `get_model_status`; useModelAvailability.ts:198-201 independently invokes the same `get_model_status` plus `get_recognition_availability_snapshot`; both re-fetch on `model-downloaded` (useModelManagement.ts:476-522 calls loadModels; useModelAvailability.ts:266-268 calls checkModels). AppContainer.tsx:266-270 derives `showOnboarding` from `modelAvailability.hasModels`, while OnboardingDesktop.tsx:369-371 derives `hasDownloadedLocalModel`/`localReady` from `modelManagement.models`. AppContainer.tsx:52-53 and 245-264 (`forceOnboardingNeedsFreshAvailability` ref, `previousHasModels` ref, `setTimeout(0)` dismissal) exist solely to reconcile the two copies' event timing.

COST: Every model event triggers 2x `get_model_status` IPC round-trips (and `no-models-error` triggers a third via checkModels at AppContainer.tsx:215). Correctness: the two caches are eventually consistent on different schedules, so onboarding can flash on/off or fail to dismiss when they momentarily disagree — e.g. after deleting the last model, `models` shows it gone while `hasModels` is still true (or vice versa), and the AppContainer ref dance is fragile, order-dependent code that any future event reordering silently breaks. Maintainability: three files must be read together to answer 'does the app think a model exists?'.

PROPOSED SLICE: Extract a single ModelCatalogContext that owns the `get_model_status` fetch and all download-lifecycle event subscriptions (progress/verifying/downloaded/error/cancelled), exposing `{models, refresh}`. Rewrite useModelAvailability to consume `models` from that context and own only the recognition-availability snapshot + remote status derivation; delete the second `get_model_status` invoke. Then delete AppContainer's `forceOnboardingNeedsFreshAvailability`/`previousHasModels` refs and the setTimeout(0) effect, since `hasModels` and `models` now update from the same fetch. Acceptance: (1) vitest with mocked `invoke` asserts exactly one `get_model_status` call per `model-downloaded`/`model-deleted` event and on the `no-models-error` path; (2) existing AppContainer.test.tsx and OnboardingDesktop.test.tsx pass unchanged in behavior — onboarding dismisses when a download completes and does not flash when hasModels flickers; (3) new test: delete-last-model drives both `models` and `hasModels` to the no-model state in the same act().

## 6. useRecording is per-instance local state mounted twice concurrently — the in-app hotkey and OnboardingDesktop each hold their own recording state machine and can disagree

EVIDENCE: useRecording.ts:30-31 (useState per caller) and 52-100 (each instance registers ~5 Tauri event listeners). Two live instances during onboarding: AppContainer.tsx:48 → useInAppRecordingHotkey.ts:107, and OnboardingDesktop.tsx:201. Both instances also independently drive the updateService singleton (useRecording.ts:105-108).

COST: Correctness: if the hotkey instance's `start_recording` invoke rejects (e.g. no input device), its copy goes 'error' but OnboardingDesktop's copy stays 'idle' — the onboarding sample step shows no error and its Record button still reads idle, while the hotkey path now behaves as errored; the reverse leaves the hotkey toggling from a stale 'idle' during an onboarding-visible error. The bail-out at useInAppRecordingHotkey.ts:290 ('state moved since keydown') also compares against a copy that may lag the sibling instance's view.

PROPOSED SLICE: Hoist useRecording into a RecordingProvider mounted once next to SettingsProvider (same pattern as ModelManagementContext); keep the hook API identical (`state, error, startRecording, stopRecording, isActive`) but read from context, so useInAppRecordingHotkey and OnboardingDesktop share one state machine and one listener set. Move the `updateService.setSessionActive` effect into the provider. Acceptance: (1) test with a spy on `listen` asserting `recording-state-changed` is subscribed exactly once with both consumers mounted; (2) test that a rejected `start_recording` invoke from one consumer is observed as `state==='error'` by the other; (3) existing useRecording.test.ts and useInAppRecordingHotkey tests pass against the provider-backed hook.

## 7. AppContainer's init effect keys on settings object identity, so every settings mutation re-runs backend history cleanup and disposes/re-initializes the update service

EVIDENCE: AppContainer.tsx:56-102 — the effect invoking `cleanup_old_transcriptions` and `updateService.initialize(settings)` (with `updateService.dispose()` in cleanup, line 100) has dependency array `[settings]`. SettingsContext.tsx:55-58 replaces the settings object on every optimistic `updateSettings`, and SettingsContext.tsx:89-111 reloads (new identity) on `model-changed`, `language-changed`, `audio-device-changed`, and `settings-changed` events. updateService.ts:145-161 shows `initialize` re-runs `checkForUpdatesInBackground()` + `setupDailyUpdateCheck()` each call; updateService.ts:357-363 shows dispose clears the daily timer.

COST: Every toggle in Settings, every model/language change (including tray-driven ones) fires a `cleanup_old_transcriptions` backend invoke — a history-store scan at src-tauri/src/commands/audio.rs:6278 — plus a dispose/initialize cycle of the update timer and a distribution-info + localStorage check. PROPOSED SLICE: Split the effect: (a) a run-once-after-settings-load effect (guard ref or `settings !== null` transition) for `cleanup_old_transcriptions`, `updateService.initialize`, and the just-updated dialog; (b) a narrow effect keyed on `settings?.check_updates_automatically` that calls a new `updateService.setAutoCheckEnabled(bool)` instead of full dispose/initialize. Acceptance: vitest on AppContainer with mocked invoke asserting `cleanup_old_transcriptions` and `updateService.initialize` are called exactly once across mount + two subsequent `updateSettings` calls + one `settings-changed` reload; toggling `check_updates_automatically` starts/stops the daily check without re-running cleanup.

## 12. Parakeet stream-session exit paths leak the sidecar's stream_busy state, wedging every later transcription until app restart

EVIDENCE: src-tauri/src/parakeet/sidecar.rs:802-810 (inactivity-timeout arm resolves final_tx and `break`s WITHOUT sending cancel_stream or killing the sidecar); same leak on the stdout-parse-error path (sidecar.rs:794-798) and the control-channel-closed path (sidecar.rs:723-725, hit when the sink is dropped without finalize/cancel, e.g. tap-worker panic). The Swift side keeps the session open and rejects heavy commands: sidecar/parakeet-swift/Sources/main.swift:311-312 replies `stream_busy` to transcribe/load while `activeStreamSession != nil`, and main.swift:959-960 rejects a new start_stream. On the Rust side, ParakeetClient only clears/respawns the sidecar on Timeout or Terminated (sidecar.rs:517-536) and on Timeout/cancelled in send_with_progress_and_cancel (sidecar.rs:588-592) — a `stream_busy` SidecarError is returned to the caller and the wedged process stays in the slot forever.

COST: Correctness: with live-preview mode on (user-selectable via `transcription_mode == "live_preview"`, commands/audio.rs:4108-4124), one stream session that ends via the 30s inactivity timeout or a noisy stdout line leaves the long-lived sidecar in stream mode; the NEXT recording's batch transcription — the actual pasted-text path — fails with `stream_busy`, and so does every one after it, until the user quits the app. Nothing in the codebase ever sends cancel_stream outside an active session, so there is no recovery path.

PROPOSED SLICE: Scope: make every exit of the open_stream session task leave the client in a known state — introduce an explicit exit enum {FinalReceived, CancelledReceived, Abort}; on Abort (timeout, parse error, control-closed) write cancel_stream and await stream_cancelled with a short (~2s) deadline, else kill the child and clear the client slot (reuse Self::clear_sidecar). Extract the session loop's write/read plumbing behind the same injectable-future pattern already used by dispatch_cancellable (sidecar.rs:236-261) so exits are unit-testable without a real process. Acceptance: unit tests per exit path assert either stream_cancelled was awaited or the slot was cleared; an integration-style test asserts that after a simulated inactivity timeout, a following client.send(Transcribe) respawns and succeeds instead of returning stream_busy. Independently shippable; no protocol change.

## 13. Busy-state has no home: the stream session holds ParakeetClient's RwLock write guard for the entire recording, so concurrent commands hang unbounded (deadline starts only after lock acquisition), while the manager papers over it by peeking global AppState

EVIDENCE: src-tauri/src/parakeet/sidecar.rs:629 — the spawned session task takes `inner.write().await` and the guard lives to the end of the task (sidecar.rs:812), i.e. for the full recording duration. ParakeetClient::send acquires the same lock in ensure() BEFORE any deadline is armed (sidecar.rs:511 then timed_request at :513), so a status/eou_model_status/download/warmup call issued mid-recording blocks for however long the user talks, with no typed error. Meanwhile busy is re-implemented twice elsewhere: ParakeetManager::real_transcription_busy reads `app.try_state::<crate::AppState>()` and matches RecordingState (manager.rs:150-166) to guard warmup (manager.rs:614-617) — the domain manager reaching into app-global UI state — and the Swift sidecar has its own `stream_busy` rejection (main.swift:311).

COST: Correctness/UX today: any UI surface or timer that calls a Parakeet command during a live-preview recording (models list refresh, warmup, status) silently freezes for the recording's duration — the per-command timeouts in messages.rs:134 never fire because they wrap only the post-lock request. Maintainability: three uncoordinated busy mechanisms (long-held lock, AppState peek, sidecar-side rejection) means the next engine gets no busy contract to implement; the cloud WS client will grow a fourth ad-hoc variant.

PROPOSED SLICE: Scope: replace the guard-held-across-session design with explicit client state — e.g. `enum ClientSlot { Idle(Option<ParakeetSidecar>), Streaming { session: SessionHandle } }` behind a short-hold mutex; non-stream commands issued while Streaming return a new typed `ParakeetError::Busy` immediately (map to a friendly message at the command layer); the session task owns the sidecar by move and returns it (or a kill decision, per issue 1) on exit. Delete real_transcription_busy's AppState peek and gate warmup on ClientSlot instead. Acceptance: unit test — status() during an open stream returns Busy in <10ms rather than blocking; warmup skipped via Busy; existing send/retry tests unchanged; cargo test green.
